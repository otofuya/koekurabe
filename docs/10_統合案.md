## 3. 価格.com・マイベストとの違い（体験）

| | 価格.com 型 | マイベスト 型 | この案 |
|---|---|---|---|
| 最初に目に入るもの | 仕様と値段の表 | 1位の商品 | 商品の絵が、声の線に並ぶ |

| 読めていない商品 | 見せ方の決まりは無い | 載らない | 「これから読みます」と見せる |

2つのサイトにもレビューや口コミはある。比べたのは「主に見せるもの」。

## 4. だれでも分かるための約束

- 画面の言葉は日常語：観点 → **気になること**、分離度が低い → **みんな同じ／みんな満足**、言及なし → **ふれていない**、段0 → **これから読みます**、条件 → **わたしと同じ人だけ**。「声札」「段」「収縮」は画面に出さない（中だけで使う）
- 1画面1問い：見出しを質問にする（「どこが気になりますか？」「サイズは合いますか？」）
- はじめての説明は1回だけ、3行
- 色だけに頼らない（左右の位置と「不満」「満足」の言葉を添える）。好み（サイズ・味）には赤も青も使わない
- 数字は必ず分母つき。押せるものは44px以上、文字は11px以上
- 一覧（カード）には順位を付けない。並びは「読めたレビューの多い順（順位ではありません）」

## 9. データは3段で数える（2026-09-25 に追加）

楽天のお店の商品のレビューには「本人が選んだ欄」（★・年代・性別・買った種類・使い道｜誰に｜はじめて／リピート）がある（[02 第12節](02_測定済みの事実.md)）。これを先に使い、AI に任せる範囲を小さくする。

| 段 | 方法 | 受け持つもの | 画面での扱い |
|---|---|---|---|
| 1 | 欄をそのまま数える（AI なし） | ★、年代・性別、また買った、贈り物・家族へ、買ったサイズ・色 | **事実**（「本人が選んだ欄」）。分母は欄に答えた人 |
| 2 | AI で1件ずつ分類 | 観点の満足・不満、好みの向き、本文に書いた条件（敏感肌・足幅が広い）、配送やお店の話を除く | **AI による分類**と明示 |
| 3 | 規模が大きくなったら置き換え（蒸留） | AI が付けた分類を正解にして小さな分類器を学習させ、自信のない分だけ AI へ | 同上 |

- 表記ゆれは AI（2段目）が吸収する。規則で難しいのは表記ゆれより**否定**（「痛くならない」と「痛くなる」）
- embedding は満足・不満の判定には使わない（否定の文どうしが近くに来やすい）。観点の辞書づくりで、似た言い回しをまとめる補助にだけ使う候補
- **欄は検証してから使う**（回数の定義・並び順の偏り・商品価格ナビに無いこと・答えた人だけの偏り）

## 10. 実装の進め方

1. **データの形を広げる**：3つの声の型・わたしの条件・数えないもの・**本人が選んだ欄**。判断は純粋関数に集めてテストで固定。レビューの読み取りで欄も残すように直す（キーなしでできる）
2. **画面を作る**：ホーム・カテゴリ（線／一覧）・商品・これに似たもの・くらべる・わたし・さがす。イヤホンの実データで（キーなしでできる）
3. 3つで抽出し直す → ゲートの値を決める（`GEMINI_API_KEY` が要る）
4. 10へ広げる（無料枠で約5日。急ぐなら有料・聞いてから）
5. 公開の準備：検索に出すページを決める（今は全部 noindex）・Amazon の審査

作り方は今の Vite ＋ TypeScript のまま（フレームワークを足さない）。アプリ化は、まずホーム画面に置ける形（PWA）から。

## 12. 見直し：条件で絞る → 声で決める（2026-09-25）

オーナーの指摘：「価格.com ならスペック比較ができる。画面のサイズとかも考えると、わざわざこのシステムで検索しないと思った」。これを受けて、第2〜10節のうち画面の流れ・見た目・言葉・作り方を見直した。キャンバスの「改訂：使いやすさ」ページ（R0〜R3）。

### 12.1 答え

- 買い物を2段に分ける：**① 条件で絞る → ② 残った2〜4つを声で決める**
- ①（仕様で絞る・最安値）は価格.com のほうが速くて正確。ここでは最小限（条件のチップ3〜4つ）にする
- ②を主役にする：**「候補をくらべる」**。価格.com などで絞った候補も、商品名を入れるだけで持ち込める
- 言い方：「スペックで分からないことを、買った人の声で。」
- 「画面のサイズ」は2通りに読んだ
  - 商品の仕様（テレビの大きさなど）として：仕様で決まる買い物は価格.com の勝ち。だから10カテゴリに入れていない（テレビ・パソコン・カメラ・スマホ本体）
  - スマホの画面の狭さとして：横に長い仕様表は作らない。くらべるのは候補3つ × 数行まで（390px に収める）

実データの例（Sony WF-C710N・129件を読んだ）：

| | 仕様の表 | 買った人 |
|---|---|---|
| つけ心地 | 無い | 不満14・満足21 |
| 連続再生 | 最大8.5時間（公式） | 電池：不満10・満足8 |
| ノイキャン | 対応（販売ページ） | 不満11・満足32 |

イヤホン97商品の絞り込み：全体 97 → 1万円まで 50 → ノイキャンあり 23（うち声を読めたのは6）。

### 12.2 6つの項目：どう変わるか

| 項目 | いまの案（第2〜10節） | 見直し後 |
|---|---|---|
| 画面の流れ | ホーム → 声の線 → 商品 → これに似たもの・くらべる | 3つの入口（商品名・カテゴリ・ほかのサイトの候補）→ 条件で絞る → 気になることで並べる → **候補をくらべる**（中心）。声の線は一覧の右上「図で見る」の寄り道 |
| 見た目 | 白地・声の2色・商品の丸が線に並ぶ | 白地・声の2色は変えない。主役を**なじみのある一覧・条件・候補のトレイ**にする。不満｜満足の帯はどの画面も同じ形 |
| 言葉 | 日常語・1画面1問い | 変えない。＋**答えを先に**（「いちばん多い不満は つけ心地（129件中14件）」「つながりは Air Pro 3 が好評」） |
| 最初の10カテゴリ | 系統をまたいで10 | 10はそのまま。**声で決まる7つ**（化粧水・シャンプー・枕・ランニングシューズ・ドリップコーヒー・プロテイン・キャットフード）を先に並べる。イヤホン・ドライヤー・掃除機は「仕様と声のズレ」を見せる |
| データの3段 | 欄 → AI → 蒸留 | 変えない。＋**仕様**を4つ目の出どころにする（公式・販売ページ・推定の印） |
| 作り方 | Vite ＋ TypeScript のまま | 変えない。＋商品と「くらべる」のページは先に HTML を書き出す（検索に出せるように）。候補は端末の中と URL（`/vs/a/b/c`） |

### 12.3 条件にする仕様の決め方（イヤホンで測った）

`data/genre-products.json` の97商品で、仕様が載っている商品の数：

| 仕様 | 商品数 | 条件にするか |
|---|---|---|
| ノイキャン | 84 / 97 | する |
| 形（耳をふさぐか） | 76 / 97 | する |
| 防水 | 58 / 97 | する |
| 連続再生 | 37 / 97 | しない（くらべる画面に出す） |
| 重さ | 34 / 97 | しない（同上） |
| 2台につなぐ | 10 / 97（すべて推定） | しない |
| 外の音を聞く | 7 / 97（すべて推定） | しない |

- **半分以上の商品に掲載がある仕様だけを条件にする。** 掲載が無い商品は外さず、一覧の一番下に残す
- 仕様の値436個の出どころ：公式 57・販売ページ 271・推定 108。推定（AI が商品名や説明から推し量った値）には画面で「推定」の印を付ける。レビューの件数には印を付けない（CLAUDE.md の1）
- イヤホン以外のカテゴリで、仕様をどこから取るかはまだ確かめていない。R2 の条件と観点は想定（観点は読んでから散らばりで決める）

### 12.4 手放すこと

- 声の線（商品を空間に並べる図）は主役でなくなる → 「図で見る」に残す（好き7・8）
- 「これに似たもの」の図は、商品ページでは「同じくらいの値段で不満が少ない2つ」に簡単にする
- 一覧は順位に見えやすい → 1位の印を付けず、並びの理由（「つけ心地の評判がいい順。順位ではありません」）を書く

### 12.6 OK のあとに作る順番

1. データの形：声・欄・**仕様（出どころつき）**。条件の判定（掲載なしを外さない）は純粋関数に集めてテストで固定
2. 画面：くらべる → 商品 → カテゴリ（条件・並び）→ ホーム → 図で見る。イヤホンの実データで
3. `GEMINI_API_KEY` が入ったら、3つのカテゴリで抽出し直す
