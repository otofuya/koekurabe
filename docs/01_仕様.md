# 何を作るか

## 一言でいうと

**購入者レビューを観点ごとに数えて、商品を比較できるサイト。**

「装着感に3件のレビューが肯定、9件が否定（レビュー37件から）」のように、**件数そのもの**を出す。
件数はコードによる集計であり推定ではないので「推定」バッジは付かない。
ただし分類自体はAIによる判定であることを画面に明示する。
レビュー本文は載せず、件数と短い引用だけを表示する。

## なぜこれなのか

カタログの仕様は「何であるか」しか言わない。「ANC対応」とは言うが「効くかどうか」は言わない。
買う理由はそこにしかない。レビューはそれを持っている。

音響誌の四象限図（解像感／音場）が価値を持つのは、**誰かが実際に聴いて置いたから**。
それを編集者1人ではなく購入者30人で、機械的に、全商品ぶんやる。

## 収益

**アフィリエイト（楽天中心・Amazonは審査通過後）。** ただし前提として：

- 「ジャンル おすすめ」は価格.com・mybest・AI Overviews と正面衝突する激戦区
- 観点別ページ（「ワイヤレスイヤホン 着け心地」）のロングテールを狙うほうが現実的
- **図はAIに要約されにくい。** テキストの答えは奪われるが、四象限やランキングの画像は
  スクリーンショットされてSNSに乗る。これが検索の外から人を連れてくる唯一の資産

単価は必ず先に確認すること。イヤホン ¥8,000 × 料率3% ＝ 1件240円。
月10万円なら約420件、逆算して月20万セッションが要る。
**地図やチャートの完成度ではなく、単価がボトルネックになりやすい。**

## 情報設計（5つのページ型）

```
/                        ホーム：ジャンル一覧＋よく語られている商品＋商品名検索
/compare/:genre          四象限／一覧のトグル、検索、価格絞り込み、カバレッジ常設
/aspect/:genre/:aspect   観点別ランキング（軸に使える観点ぶん自動生成・検索流入の受け口）
/reviews/:productId      商品の評判＋まとめ＋公式スペック補足＋購入
/vs/:a/:b                2商品比較（URL化してシェア可能に）
```

### `/` ホーム
ジャンルごとに**カバレッジを明記**（「97件中24件のレビューを読めています（のべ1,780件）」）。
よく語られている商品を、褒められた点と不満点を**同じ大きさで**並べる。商品名検索を前面に。

### `/compare/:genre` 四象限
既定の2軸はジャンルごとに人手で決める（イヤホンなら 装着感 × ノイズキャンセリング）。
- 軸の変更は「小さな倍数」で選ばせる。**選べない観点も理由付きで灰色表示する**
- 一覧トグル。一覧には**未読の商品も名前を出す**
- 価格絞り込みは減光（消さない）

### `/aspect/:genre/:aspect` 観点別ランキング
順位表＋**1行ずつ引用**。言及の無い商品は最下位ではなく別リスト。
分離度ゲートを通らない観点は**ページを作らない**（404）。

### `/reviews/:productId` 商品ページ
**評判が上、仕様が下。** レビューの観点バー（分母つき）→ まとめ（件数から機械生成）→
公式スペック（「推定」バッジ）→ 購入ボタン。弱い観点から他商品へ送る導線も置く
（うち1件は「こちらも不満が多め」と正直に書く）。

### `/vs/:a/:b` 2商品比較
観点ごとに左右。**どちらも言及が無い観点は両側に「言及なし」と書く**
（片側だけ空欄だと、空欄側が劣って見える）。

## データの流れ

```
楽天の商品リスト（メーカー基準で絞る・画像必須）
  ↓ fetch-reviews.mjs        製品ページのレビュー（ページ送り・numFound を見る）
  ↓ fetch-shop-reviews.mjs   店舗のレビュー（深さを足す）
  ↓ extract-aspects.mjs
  │  1. 製品ページと店舗ページのレビューを本文ハッシュで重複排除
  │  2. レビューを個別に番号付きで Gemini に送り、観点×肯否を判定させる
  │  3. 件数はコードが集計する（Gemini には数えさせない）
  │  4. 引用を原文と照合し、通らないものは件数ごと捨てる
  │  5. positive <= reviewsRead 等の不変条件を検証し、違反があれば失敗する
data/genre-aspects.json      商品ごとの { 観点, 肯定, 否定, 引用[], レビュー数 }
  ↓ aspect-model.ts          収縮・分離度・軸ゲート・配置・順位・まとめ（純粋関数）
画面
```

**件数はAIによるレビュー分類の集計結果である。** 「レビュー37件中11件が装着感に言及」は
Gemini が各レビューを観点ごとに肯定・否定に分類した結果をコードが数えたもので、
人手で数えた件数ではない。分母（レビュー数）と集計操作自体は検証可能な事実だが、
「この文は装着感への肯定である」という判断はAIの推論である。

## 観点（アスペクト）はカテゴリごとに人手で定義する

自由文から発見させてはいけない（構造的に固有名詞が出る）。
イヤホンでの実績のある10個：

```
音質 / 低音 / 装着感 / ノイズキャンセリング / 外音取り込み /
バッテリー / 接続の安定 / 操作性 / 通話品質 / 価格の納得感
```

各観点は「良い側の言葉」と「悪い側の言葉」を持つ（極として図に出す）。
例：装着感 → 「つけ心地が良い」↔「合わない人がいる」

## 公開ゲート

| 条件 | 値 | 実装 |
|---|---|---|
| 軸に使える観点 | 2つ以上 | `offerableAxes` |
| 言及した商品数（観点ごと） | 8商品以上 | `MINIMUM_MENTIONING_PRODUCTS` |
| 複数回言及された商品数（測定対象） | 6商品以上 | `MINIMUM_MEASURED_PRODUCTS` |
| 分離度（散らばり） | 0.35以上 | `MINIMUM_SEPARATION` |
| 両軸に言及がある商品 | 6商品以上 | `axisPairs` の `minimumBoth` |
| 不変条件（positive ≤ N かつ negative ≤ N） | 全商品で通過 | `checkProductInvariants` |
| 重複排除 | 実行済み | `deduplicateReviews` |
| 抽出完全性 | 全レビューが分類済み | `extract-aspects.mjs` の strict モード |
| 一括判定 | 上記すべて | `checkPublishability` + `resolveDefaultAxes` |

満たさないジャンルはリンクしない（`checkPublishability` が判定する）。
不変条件に違反するデータは公開しない（`validate:data` がビルド前に検証する）。

## やらないと決めたこと

- **診断（推し3つ→あなたの位置）。** シェアは図そのもので行う
- **さくら度判定。** ただし収縮の副産物として、レビューが少ない商品は自然に中央に集まる
- **Amazon のレビュー本文取得。** 選択的なアクセス制御がかかっている（`02_測定済みの事実.md`）
- **UMAP による商品地図。** カタログテキストが無く、座標がブランドで固まる（同上）
